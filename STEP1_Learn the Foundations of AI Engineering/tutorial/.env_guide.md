# The .env File Guide: Managing Secrets and Configuration

## The Problem: Hardcoded Secrets

Right now, your code likely has "Secrets" or "Settings" hardcoded inside it. Maybe it looks like this:

```python
# database.py
API_KEY = "sk-1234567890abcdef"  # 😱 DANGER!
DB_PASSWORD = "my_secret_password"
BATCH_SIZE = 32
```

### Why This is Bad

1. **Security**: If you push this code to GitHub, the whole world sees your API key. (Bots scan GitHub for keys constantly).
2. **Flexibility**: If you want to run this on your colleague's machine, they might need a different database password. They have to edit your code to fix it.

## The Solution: The .env File

An **environment variable** is a variable that lives in your operating system, not your Python script. A `.env` file is a simple text file that lets us manage this easily for our project.

## 1. The Setup

First, you create a file named simply `.env` (no name, just the extension) in your project root (next to `pyproject.toml` and `src`).

Inside `.env`, you write your settings like simple key-value pairs:

```bash
# .env file content
OPENAI_API_KEY=sk-1234567890abcdef
DATABASE_URL=postgres://user:pass@localhost:5432/mydb
MODEL_BATCH_SIZE=32
```

**Important Notes:**
- No spaces around the `=` sign
- No quotes are usually needed (unless the value itself contains spaces)
- One key-value pair per line
- Lines starting with `#` are comments

## 2. Loading it in Python

Python doesn't read this file automatically. We need a helper library. Since you are using `uv`:

```bash
uv add python-dotenv
```

Now, in your code (usually in `src/__init__.py` or at the top of `main.py`), you load these variables:

```python
import os
from dotenv import load_dotenv

# 1. Load the variables from .env into the OS environment
load_dotenv()

# 2. Access them safely
api_key = os.getenv("OPENAI_API_KEY")
batch_size = int(os.getenv("MODEL_BATCH_SIZE", "16"))  # Default to 16 if missing
```

### Best Practices for Loading Environment Variables

- **Always provide defaults** for non-sensitive configuration values:
  ```python
  batch_size = int(os.getenv("MODEL_BATCH_SIZE", "16"))
  ```

- **Validate required secrets** and fail fast if they're missing:
  ```python
  api_key = os.getenv("OPENAI_API_KEY")
  if not api_key:
      raise ValueError("OPENAI_API_KEY environment variable is required!")
  ```

- **Load early**: Call `load_dotenv()` as early as possible in your application, ideally at the top of your main entry point.

## 3. The Golden Rule of .env

There is one rule you must never break:

> **NEVER commit your `.env` file to Git.**

If you commit it, your secrets are still in public history. To prevent this, you immediately add `.env` to your `.gitignore` file.

```plaintext
# .gitignore
__pycache__/
*.pyc
.env  <-- IMPORTANT
```

### Why This Matters

- Even if you delete a file from Git, it remains in the Git history
- Anyone with access to your repository can see all previous commits
- Bots constantly scan public repositories for exposed secrets
- Once a secret is exposed, consider it compromised and rotate it immediately

## 4. How Do Teammates Know What to Set?

If you hide your `.env` file, how does a new developer know which variables they need to create?

We create a **template file** called `.env.example`. It contains the keys, but none of the secrets.

```bash
# .env.example (Safe to commit to Git ✅)
OPENAI_API_KEY=
DATABASE_URL=
MODEL_BATCH_SIZE=32
```

**Workflow:**
1. Your teammate clones the repo
2. They see `.env.example`
3. They copy it to `.env`: `cp .env.example .env` (or `copy .env.example .env` on Windows)
4. They fill in their own real keys

### .env.example Best Practices

- Include all required environment variables
- Provide example values for non-sensitive settings (like `MODEL_BATCH_SIZE=32`)
- Leave sensitive values empty (like `OPENAI_API_KEY=`)
- Add comments to explain what each variable does:
  ```bash
  # OpenAI API key for language model requests
  OPENAI_API_KEY=
  
  # Database connection string
  DATABASE_URL=
  
  # Number of items to process in each batch
  MODEL_BATCH_SIZE=32
  ```

## 5. Complete Project Setup Checklist

When starting a new project:

1. ✅ Create `.env` file in project root
2. ✅ Add your secrets and configuration to `.env`
3. ✅ Create `.env.example` with the same keys (no secrets)
4. ✅ Add `.env` to `.gitignore`
5. ✅ Commit `.env.example` to Git
6. ✅ Install `python-dotenv`: `uv add python-dotenv`
7. ✅ Load environment variables early in your code: `load_dotenv()`

## 6. Common Mistakes to Avoid

### ❌ Spaces Around the Equals Sign
```bash
# WRONG
DB_PASS = super_secret_123

# CORRECT
DB_PASS=super_secret_123
```

### ❌ Putting .env in the Wrong Location
- ✅ Correct: `.env` in project root (same level as `pyproject.toml`)
- ❌ Wrong: `.env` inside `src/` or other subdirectories

### ❌ Committing .env to Git
- Always verify `.env` is in `.gitignore` before your first commit
- Use `git status` to check what files will be committed

### ❌ Not Providing Defaults
```python
# WRONG - Will crash if variable is missing
batch_size = int(os.getenv("MODEL_BATCH_SIZE"))

# CORRECT - Provides a sensible default
batch_size = int(os.getenv("MODEL_BATCH_SIZE", "16"))
```

## 7. Advanced: Environment-Specific Files

For larger projects, you might want different configurations for development, testing, and production:

```bash
.env.development
.env.test
.env.production
```

You can load a specific file:

```python
from dotenv import load_dotenv
import os

env = os.getenv("ENVIRONMENT", "development")
load_dotenv(f".env.{env}")
```

## 8. Quick Quiz: The Config Check

Imagine you have the following code in `main.py`:

```python
import os
from dotenv import load_dotenv

load_dotenv()
print(f"Connecting to database with password: {os.getenv('DB_PASS')}")
```

You run the script, and it prints: `Connecting to database with password: None`

Your `.env` file looks like this:

```bash
DB_PASS = super_secret_123
```

**Question:** Based on the syntax rules we discussed, why is `os.getenv` failing to find the password?

**A.** You forgot to import `sys`.  
**B.** You have spaces around the `=` sign in the `.env` file.  
**C.** The `.env` file is in the `src` folder instead of the root.

**Answer:** **B** - You have spaces around the `=` sign. The `.env` file format requires no spaces: `DB_PASS=super_secret_123`

## Summary

- ✅ Use `.env` files to store secrets and configuration
- ✅ Load them with `python-dotenv` and `load_dotenv()`
- ✅ **NEVER** commit `.env` to Git
- ✅ Always create `.env.example` as a template
- ✅ Add `.env` to `.gitignore` immediately
- ✅ Provide defaults for non-sensitive configuration
- ✅ Validate required secrets and fail fast if missing

By following these practices, you'll keep your secrets safe and make your projects more flexible and maintainable!
